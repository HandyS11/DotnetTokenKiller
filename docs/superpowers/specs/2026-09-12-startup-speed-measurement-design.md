## Context

This is the first of four sub-projects on `perf/startup-speed`, which aims to cut what dtk costs
per invocation. Measurements taken while scoping the work (Ryzen 5 3600, Linux, `dtk pipe build`
over `dotnet_build_errors.txt`, median of 21 runs):

| Build | `--version` | tracking on | tracking off | 1 MB log, tracking on |
|---|---:|---:|---:|---:|
| JIT, as shipped | 115 ms | 295 ms | 216 ms | 532 ms |
| ReadyToRun | 70 ms | 219 ms | 146 ms | 408 ms |
| Native AOT (Spectre rooted) | 12.6 ms | 65 ms | 14.8 ms | 141 ms |

The sub-projects, in order:

1. **Measurement** (this spec): time the wrapped-command path, not just `pipe`.
2. **Tracking path:** `TieredPGO` off, fewer SQLite statements per run, tokenizer and database
   setup started in the background while the child process runs.
3. **Native AOT distribution:** trim-safety fixes, RID-specific tool packages, an AOT CI job.
4. **Tokenizer spooling:** deferred until AOT shows what remains.

## Problem

`cold-start` times `dtk pipe build` only. That path reads stdin to the end before any work starts,
so it measures dtk's cost as a strictly serial tax. The path users actually run, `dtk dotnet build`,
is shaped differently: dtk starts, launches `dotnet`, streams its output into the tee log while it
runs for seconds, and only then filters and tracks.

Two consequences:

- **The wrapped path is unmeasured.** `ProcessCommandRunner.RunStreamedAsync`, the per-line pump
  into the tee writer and the stdout/stderr concatenation never run under `cold-start`.
- **Sub-project 2's main change would be invisible.** Loading the tiktoken vocabulary (~110 ms) and
  opening SQLite (~39 ms cold) in the background while the child runs removes wall-clock time only
  when there is a child to overlap with. `pipe` has none, so it would report no gain.

A real `dotnet build` cannot be the child: per project history, build-spawning tests do not run
reliably on a developer machine, and a build's own variance would swamp a sub-second overhead.

## Solution

`cold-start` gains two scenarios beside the existing one, all printed by the same verb so the
Benchmarks workflow's existing step captures them without change:

1. **`pipe build`**, unchanged, so the recorded 287.9 ms figure stays comparable.
2. **`dotnet build`, instant child:** a fake `dotnet` prints the fixture and exits. dtk's serial
   cost on the wrapped path.
3. **`dotnet build`, delayed child:** the fake `dotnet` sleeps 1000 ms first, then prints the
   fixture. Longer than the vocabulary load and SQLite setup combined, so background setup can
   overlap it completely.

### The fake `dotnet`

A POSIX shell script generated by a new `Support/FakeDotnet` class into a directory under the
`HermeticState` temp root, beside a copy of the fixture:

```sh
#!/bin/sh
sleep 1          # delayed scenario only
cat '<root>/output.txt'
exit 1
```

It is marked executable with `File.SetUnixFileMode`. The script ignores its arguments. Its own
cost is a shell start and a `cat`, one to two milliseconds.

`ProcessCommandRunner` launches the bare name `dotnet`, resolved through `PATH`. The script's
directory is prepended to `PATH` **only on the `ProcessStartInfo` of the processes that must find
it** (dtk in scenarios 2 and 3; the child-alone calibration run spawns the script by its absolute
path), never with `Environment.SetEnvironmentVariable`. The harness itself runs under `dotnet run`
and must keep resolving the real SDK.

Rejected alternatives: re-launching the benchmark runner as `dotnet` through a symlink would work on
Windows but makes the child a .NET process with its own ~50 ms of JIT noise; a native helper binary
is precise but adds a toolchain to the benchmarks build.

### Measuring overhead

Scenario 1 keeps its current sampling: wall-clock per spawn.

Scenarios 2 and 3 sample in **pairs**. Each iteration runs the fake child alone, then dtk wrapping
it, and records `wrapped − child`. The report prints the median and p95 of those differences as
dtk's overhead, and the median wrapped wall-clock beside it. Pairing adjacent runs cancels machine
drift over the ~3 minute run, which subtracting two independently collected medians would not.

The delayed child sleeps, so the CPU is idle while it runs. That is the **best case** for
background setup: a real build competes for every core. The instant scenario is the worst case.
The report says so in its section header. For output this fixture's size (2.6 KB), the true cost
of a real build lies between the two; dtk's per-line tee flush and token counting grow with output
size, so this bracket says nothing about a much larger build log.

All scenarios keep 5 warmup + 50 measured iterations: fifty is the floor at which a p95 is worth
printing. Scenario 3 dominates the runtime at about 50 × 2.3 s; the whole verb takes about three
minutes.

### Failing loudly

A sample counts only if dtk exits `1` **and** its stdout contains the first non-empty line of the
build filter's in-process output for the fixture (computed through `SavingsScenarios.FilterFor`).
The exit code alone is not enough: if `PATH` wiring ever broke and the real SDK ran, `dotnet build`
with no project also exits `1`, and the harness would report a plausible timing for the wrong
program. The same output check is applied to scenario 1, which today checks the exit code only.

The child-alone calibration run must also exit `1`, and print the fixture.

Exit code and output still cannot prove the tracking step ran: `FilteredOutputPipeline` swallows
every exception a tracking attempt raises (a faulted tokenizer load, a SQLite failure), by design,
so the user's workflow is never broken by it — which also means dtk still exits and prints
normally having silently skipped that work. After each scenario finishes sampling, `cold-start`
reads the tracking database directly and requires every run in that scenario to have recorded a
row with a positive input-token delta; otherwise it throws rather than reporting a number.

On Windows the verb exits non-zero before measuring anything, explaining that the wrapped scenarios
need a POSIX shell. The Benchmarks workflow runs on `ubuntu-latest`, so no CI path is affected.
That workflow pipes `cold-start`'s output through `tee` to save it as an artifact; the step begins
with `set -o pipefail` so the step fails when `cold-start` does; without it, `bash -e` takes only
`tee`'s exit code and a failing measurement would still report green.

### Documentation

CLAUDE.md's Benchmarks section describes the three scenarios and records their numbers measured
on the same machine as the existing tokenizer figures, dated, so sub-project 2 has a baseline to
compare against.

## Testing

The benchmarks project has no test project, and this change does not add one: the harness is a
measurement tool whose only meaningful test is running it.

Verification:

- `cold-start` completes and prints all three sections with plausible figures: scenario 2's
  overhead in the same few-hundred-millisecond range as scenario 1's wall-clock; scenario 3's
  overhead median within about 10 ms of scenario 2's (while dtk does no background setup); and
  scenario 3's wrapped wall-clock approximately 1000 ms plus scenario 3's own overhead plus a few
  ms of the child's own cost (sleep overshoot, shell start, `cat`). An earlier version of this
  bound — wall-clock above 1000 ms by no more than scenario 2's overhead — omitted that last part,
  the fake child's own cost.
- Every scenario's dtk runs must each have recorded a tracking row (see Failing loudly): a scenario
  whose timings look plausible but whose tracking step silently failed for some runs does not pass.
- Temporarily breaking the fake child (wrong exit code, or not printing the fixture) makes the run
  fail with the child's output, rather than report a number.
- The existing `SavingsBaselineTests` and the rest of `dotnet test` stay green; nothing under `src/`
  changes.

## Out of scope

- Any change to dtk itself. Sub-projects 2–4 have their own specs.
- Running the wrapped scenarios on Windows.
- Simulating a CPU-bound child. It would narrow the gap between the two scenarios but needs
  calibration per machine, and the two bounds already bracket the real cost.
- Timing the AOT or ReadyToRun builds in CI. `cold-start` already accepts a binary path, which
  is enough for local comparison until sub-project 3 decides how those binaries are produced.
